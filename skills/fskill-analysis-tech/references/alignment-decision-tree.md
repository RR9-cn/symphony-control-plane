# 沟通对齐与 Grilling 式盘问

本文件用于步骤 3/4/4.5/5：通读材料后、正式写正文前，帮助 Agent 与用户形成共享理解。

这里的“决策树”只提供推荐推演方向，不是固定问卷。Agent 必须根据本次需求的真实复杂度，围绕技术闭环、冲突点、模糊点、扩展点和风险点自适应深挖。

## 真实意图

沟通对齐不是为了把下面清单逐条问完，而是为了在写技术分析前解决这些问题：

- 技术范围是否准确，是否继承或修正上阶段决策。
- 核心流程、状态机、接口、DDL 是否彼此闭环。
- PRD、任务拆分、接口文档、DDL 之间是否有冲突。
- 材料中模糊或缺失的部分是否影响技术实现。
- 是否存在 PRD 没提但技术上必须补齐的接口、任务、MQ、回调、缓存、审计、幂等、锁、事务、降级。
- 哪些高敏或高扩展能力必须单独设计，避免后续编码写散。
- 哪些问题可由 Agent 查材料、查数据库、查代码自行回答，哪些必须请用户拍板。

最终目标是：用户和 Agent 对本次技术方案已经达到共享理解，然后再进入大纲确认和正文撰写。

对齐沟通的默认重心应放在**技术设计与扩展约束**，而不是把产品/技术交叉细节都抛给用户确认。Agent 需要先基于材料、工程经验和既有架构做技术判断，输出“问题 -> Agent 决策 -> 影响”的对齐清单；只有真正需要用户参与定义的问题才显式提问。

## 双轨对齐结构

整个对齐过程拆成两条轨道执行：**产品向对齐**和**技术向对齐**。两条轨道都必须先由 Agent 自行推演、列出默认决策和影响，再筛选少量必须用户参与的问题。

### 轨道 A：产品向对齐

目标：专门解决**卡在产品方案和技术方案之间**的问题：产品文档没有明确说明、没有提及或描述过于理想化，但这些内容会直接改变技术方案的边界、复杂度、数据模型、权限模型、状态机、事务一致性、缓存策略、审计追责或上线风险。

产品向对齐不是泛产品评审，也不是替产品补完整 PRD；它的落点始终是：**这些产品规则或产品取舍会如何影响技术方案设计**。Agent 需要把产品材料中的沉默、模糊和理想化假设转译成技术决策分叉，再判断哪些可以默认写入技术分析，哪些必须显式请用户确认。

产品向对齐重点处理三类问题：

| 类型 | 判断标准 | 示例 | 技术影响 |
|---|---|---|---|
| 产品未明确但会造成技术分叉 | PRD 有相关需求，但关键规则没说清，不同答案会导向完全不同的实现 | 权限更新后是实时生效，还是允许用户重新登录后生效 | 实时生效可能需要权限缓存精确失效、前端/后端实时校验、token/session 版本控制；重新登录生效则链路更简单但体验和风险不同 |
| 产品未提及但技术闭环可能必须补齐 | PRD 只描述业务动作，但从技术和运营追责看，缺少必要承载 | PRD 只说“修改权限”，但技术侧判断高敏操作通常需要操作审计 | 可能需要新增审计表、审计 Manager、操作前后摘要、traceId、失败原因和查询入口 |
| 产品理想方案与技术成本/风险不匹配 | PRD 默认最理想体验，但技术实现成本、上线周期或风险显著上升，存在可接受的产品妥协空间 | 权限修改要求实时生效，但若允许“重新登录后刷新权限”，V1 成本明显降低 | 需要让用户确认体验、风险和上线速度的取舍，并反映到缓存、鉴权、前端刷新和登录态方案中 |

关注内容：

| 关注点 | 说明 | 示例 |
|---|---|---|
| 范围边界影响 | 本次做/不做哪些模块、接口、页面、任务、回调；范围变化是否改变技术闭环 | M8/M10 是否排除本轮；若排除，是否仍要预留接口/字段 |
| 业务语义影响 | 同一术语在 PRD/DDL/API 中是否含义一致；语义差异是否改变表结构、状态机或接口契约 | “删除员工”是停用、软删除，还是解除商户关系 |
| 生效时机影响 | 配置、权限、状态、价格、规则变更是立即生效、下次登录生效、次日生效，还是仅对新数据生效 | 权限修改后立即踢出旧 token，还是用户重新登录后刷新权限 |
| 操作对象影响 | 谁操作谁，是否跨商户/门店/角色层级；是否存在自操作、最后管理员、上级改下级等边界 | 管理员是否能停用自己或最后一个管理员 |
| 高敏动作影响 | 涉及权限、账号、密码、手机号、资金、实名、关键配置时，产品是否说明二次校验、审计、通知和失效规则 | 修改角色权限后是否记录操作前后权限差异 |
| 隐含闭环影响 | 产品只描述正向动作，但技术上是否需要补审计、幂等、缓存失效、补偿、告警、人工处理入口 | 修改权限成功后是否删除权限缓存、写审计、通知被影响用户 |
| 成本风险取舍 | 产品期望是否显著提高技术复杂度；是否存在 V1 可接受的简化方案 | 权限实时生效 vs 重新登录后生效 |
| 用户可恢复性影响 | 误操作或失败后是否有恢复、重试、撤销、客服处理入口；没有恢复能力是否可接受 | 错误收回权限后是否能恢复原权限集合 |
| 风险接受影响 | 某些业务后果是否可接受，且该接受会改变技术防护强度 | 唯一管理员被禁用后商户无人管理 |

产品向对齐的输出不是产品方案，而是**产品规则对技术方案的影响结论**。推荐在输出时把问题分成“Agent 可默认决策”和“必须用户确认”两类：

- `Agent 默认决策`：产品未写但技术上属于成熟默认做法，或不改变对外契约、成本较低、风险收益明确的内容，例如权限变更后删除权限缓存、后端统一鉴权、关键操作写业务日志。
- `需要用户确认`：不同选择会改变 DDL/API、权限模型、登录态/缓存方案、状态机、上线范围、合规安全、用户体验或工作量级别，例如权限实时生效还是重新登录生效、是否新增审计表、是否接受 V1 延迟生效。
- `记录风险/待定`：产品目标明确但技术代价较高，当前无法拍板且不阻塞其他章节时，先记录为风险或待定，不把不确定性隐藏进默认方案。

输出格式：

```markdown
| 产品向问题 | Agent 理解/默认决策 | 技术影响 | 处理方式 |
|---|---|---|---|
| {{问题}} | {{结论}} | {{影响接口/DDL/状态机/权限/流程}} | {{继承/Agent 默认决策/需要用户确认/风险}} |
```

典型问题示例：

| 产品向问题 | Agent 理解/默认决策 | 技术影响 | 处理方式 |
|---|---|---|---|
| 权限修改后的生效时机未说明 | 倾向 V1 采用“服务端权限缓存失效 + 新请求按最新权限校验”，是否需要踢出旧登录态需确认 | 影响 token/session 版本、权限缓存、前端菜单刷新、接口鉴权和测试范围 | 需要用户确认 |
| PRD 只写修改权限，未提审计 | 权限属于高敏动作，默认补操作审计能力 | 可能新增审计表/审计字段，记录操作者、目标对象、变更前后摘要、traceId | Agent 默认决策；若新增表需用户确认 |
| 产品期望权限实时生效，但实现成本高 | 建议明确 V1 是否可接受“重新登录后刷新权限”或“后端实时、前端菜单下次刷新” | 影响上线速度、前后端改造量、用户体验和越权风险 | 需要用户确认 |
| 删除/停用员工语义未区分 | 默认不把“停用”当作物理删除；历史数据和审计保留 | 影响状态字段、唯一索引、列表过滤、登录拦截和恢复路径 | 需要用户确认或继承既有决策 |

### 轨道 B：技术向对齐

目标：确认技术方案、扩展约束、组件边界和工程落地方式，是技术分析的主要注意力所在。

关注内容：

| 关注点 | 说明 | 示例 |
|---|---|---|
| 架构边界 | 哪些能力抽组件，放在哪层，谁调用谁 | `PermissionManager` / `DataScopeManager` |
| 横切能力 | 鉴权、权限、审计、日志、脱敏、限流是否统一设计 | 自定义权限注解 + AOP/Interceptor |
| 高敏能力 | 密码、手机号、账号注销、权限变更是否有二次校验、审计、失效 | 修改手机号后 `token_version + 1` |
| 强扩展点 | 后续高概率扩展的能力是否写死 | 短信 `SmsSender` 策略，多供应商路由 |
| 技术方案选型 | 核心链路用同步接口、MQ、定时任务、afterCommit、Outbox、本地消息表还是状态机/流程编排 | 支付成功后余额入账用 MQ 推进，定时任务做兜底对账 |
| 数据一致性闭环 | 明确强一致/最终一致边界、事务边界、事件可靠性、补偿、对账和人工处理 | 下单扣库存成功但支付单创建失败如何回滚或释放库存 |
| 核心流程技术闭环 | 从入口、校验、数据变更、异步事件、外部回调、缓存审计到补偿兜底形成完整技术链路 | 下单 -> 锁库存 -> 支付回调 -> 确认库存 -> 商家余额入账 -> 流水审计 -> 兜底查单 |
| 事务一致性 | 事务边界、锁、幂等、缓存失效、事务后副作用 | 短信 afterCommit，失败不回滚主业务 |
| DDL/API 承载 | 字段、索引、枚举、接口参数是否支撑方案 | 软删除唯一约束包含 `deleted_at` |
| 可观测与兜底 | 审计、告警、traceId、失败原因、人工处理入口 | `mch_operation_audit_log` |

技术向对齐的输出应优先是 Agent 默认技术决策；只有命中用户参与门槛时才提问：

```markdown
| 技术设计点 | Agent 技术决策 | 影响 | 处理方式 |
|---|---|---|---|
| {{设计点}} | {{组件/模式/边界/兜底}} | {{扩展性/风险/开发落点}} | {{Agent 默认写入/需要用户确认/待定}} |
```

执行顺序：

1. 先做产品向对齐，快速收敛范围、语义、状态和风险接受；不要陷入页面文案、交互细节或可由 Agent 推断的产品规则。
2. 再做技术向对齐，系统性检查架构、组件、扩展、事务、幂等、缓存、审计、降级和 DDL/API 承载力。
3. 最后合并两条轨道的结论，执行遗漏决策反省和最终补充确认。

技术向对齐必须额外完成“方案选型与闭环推演”：

| 推演项 | Agent 默认判断规则 | 需要输出的结论 |
|---|---|---|
| 同步接口 | 用户请求内必须立即得到结果、且事务边界可控的动作才放同步链路 | 哪些步骤同步完成，哪些步骤不能拖进主事务 |
| MQ | 需要解耦、削峰、异步推进下游状态，且允许最终一致的动作优先 MQ | 事件名称、生产时机、消费方、幂等键、失败重试 |
| 定时任务 | 超时关闭、扫漏、补偿、查单、对账等兜底场景优先定时任务 | 扫描条件、处理状态、重试次数、告警/人工处理 |
| afterCommit | 主事务提交后才能执行的短信、缓存失效、审计、MQ 发送等副作用优先 afterCommit | 副作用失败是否回滚主业务、如何补偿 |
| Outbox/本地消息表 | 主数据提交成功但事件不能丢失时，考虑可靠事件机制 | 消息落表、发送状态、补偿任务、幂等消费 |
| 状态机/流程编排 | 多阶段状态推进、外部回调、异步补偿交织时，必须显式状态机视角 | 状态由谁推进、失败停在哪、如何恢复推进 |

Agent 对每个核心流程必须输出“推荐实现路径 + 为什么不用其他路径 + 一致性/失败兜底”。只有当选型会引入新中间件、云服务、成本、运维复杂度、合规风险或长期架构路线变化时，才显式询问用户。

必须显式提问的用户参与门槛：

| 类型 | 说明 | 示例 |
|---|---|---|
| 业务语义取舍 | 不同选择代表不同产品规则、责任边界或用户体验 | 账号注销是注销整个账号还是当前商户身份 |
| DDL/API 契约变化 | 会新增表/字段/索引、删除字段、改变接口出入参或错误码语义 | 新增操作审计表、软删除唯一约束是否纳入 `deleted_at` |
| 长期架构取舍 | 会影响多个模块、后续扩展路线或团队协作边界 | 权限字典表 vs 代码枚举元数据 |
| 合规/安全风险接受 | 会影响账号、密码、手机号、权限、资金、隐私或审计追责 | 账号注销是否允许导致商户无人管理 |
| 外部依赖与成本 | 会引入新中间件、SDK、云服务、费用或运维责任 | 是否引入 MQ、是否接入多短信供应商 |

不应显式提问、由 Agent 自行决断并写入技术分析的内容：

| 类型 | Agent 处理方式 | 示例 |
|---|---|---|
| 常规工程实现 | 直接给出推荐设计和影响 | 后端接口权限校验使用自定义注解 + AOP/Interceptor |
| 可从材料推导的闭环 | 写入“已确认继承/默认写入” | 修改手机号后 `token_version + 1` 失效旧 session |
| 不改变外部契约的组件边界 | 写入核心技术设计章节 | 抽 `DataScopeManager` 统一数据范围过滤 |
| 可逆或低风险实现细节 | 写入推荐方案，不盘问用户 | 权限缓存短 TTL + 变更后精确删除 |
| 行业内成熟模式 | 直接采用，并说明禁止事项 | 短信发送抽策略接口，支持阿里云/未来多供应商切换 |

## Grilling 操作规约

按下面方式执行，而不是机械套模板：

1. 先自行推演：基于 PRD、任务拆分、接口、DDL、决策记录、技术栈和可查代码，先画出 Agent 自己理解的方案路径。
2. 先复读既有决策：进入盘问前必须读取 `decision-log.md`、DDL 设计假设和已有技术分析中的确认项，建立“已确认决策索引”。索引至少包含决策点、结论、来源位置、影响模块。
3. 先查再问：如果问题能通过重读材料、查表结构、搜索代码库或已确认决策索引回答，就自行查证，不要问用户。
4. 不重复确认：已确认决策只能作为继承结论引用，不得再次提问确认；只有出现新材料冲突、实现约束变化、用户主动要求重议时，才允许重新打开该决策，并必须说明“为什么这不是重复提问”。
5. 沿设计树深挖：从核心流程出发，逐分支追到状态机、数据模型、事务、幂等、异常、缓存、权限、审计、风险和扩展点。
6. 解析依赖关系：先解决会阻塞后续判断的问题，再问依赖它的下游问题。
7. 每轮只问一个问题：不要把多个问题打包给用户。每个问题必须等用户反馈后再继续。
8. 每个问题带推荐答案和备选方案：问题里要写清 Agent 推荐怎么定、为什么这么定、可选备选方案是什么、如果采用备选方案有什么影响。
9. 问真实问题：只问影响本次技术分析结论的问题，不问为了填模板而产生的问题。
10. 先自决策再提问：产品/技术交叉问题或纯技术问题，若 Agent 能根据材料、代码、DDL、既有架构和工程常识作出稳妥判断，应先列入“Agent 默认决策清单”，说明影响，不要直接问用户。
11. 提问要过门槛：只有命中“必须显式提问的用户参与门槛”的问题，才进入逐个盘问。
12. 不急着定稿：在用户确认“已经达成共享理解”前，不进入正式撰写，不交付最终技术分析正文。

可直接遵循这段行为准则：

> Interview me relentlessly about every aspect of this plan until we reach a shared understanding. Walk down each branch of the design tree, resolving dependencies between decisions one-by-one. For each question, provide your recommended answer.
>
> Ask the questions one at a time, waiting for feedback on each question before continuing. Asking multiple questions at once is bewildering.
>
> If a question can be answered by exploring the codebase, explore the codebase instead.
>
> Do not enact the plan until I confirm we have reached a shared understanding.

## 步骤 3 输出材料理解

进入提问前，先向用户展示材料理解。不要直接开始问。

必须按“双轨”展示材料理解，先产品向，后技术向。

产品向必须包含：

| 清单 | 说明 |
|---|---|
| 本次范围 | 来自任务拆分表和用户确认的模块/接口 |
| 继承的上阶段决策 | 来自 `decision-log.md`，包括范围、链路、状态机、依赖 |
| 已确认决策索引 | 来自 `decision-log.md`、DDL 设计假设、已有技术分析；标注哪些问题本次直接继承、不再重复提问 |
| Agent 推演出的核心路径 | 按真实业务主线描述，不按接口罗列 |
| 已发现冲突点 | PRD、接口、DDL、任务拆分、代码之间的不一致 |
| 已发现模糊点 | 影响技术实现但材料没有说清的内容 |
| 产品向 Agent 默认决策 | Agent 可自行决定的业务/技术交叉问题、决策和影响 |
| 产品向必须用户拍板项 | 命中业务语义、范围、状态、风险接受门槛的问题 |

技术向必须包含：

| 清单 | 说明 |
|---|---|
| 技术闭环候选 | PRD 未显式提到但技术上可能必须补齐的能力 |
| 疑似核心技术设计点 | 横切能力、高敏能力、强扩展点、统一组件 |
| 技术方案选型候选 | 同步接口、MQ、定时任务、afterCommit、Outbox、状态机/流程编排等实现路径的推荐选择 |
| 数据一致性闭环候选 | 强一致/最终一致边界、事务、锁、幂等、补偿、对账、人工处理入口 |
| 核心流程技术闭环候选 | 从入口到数据变更、异步事件、外部回调、缓存审计和兜底任务的完整技术链路 |
| 可自行查证项 | Agent 将继续查材料/表/代码，不询问用户 |
| 技术向 Agent 默认决策 | Agent 能自行决定的组件、模式、边界、兜底方案和影响 |
| 技术向必须用户拍板项 | 命中 DDL/API、长期架构、合规安全、成本或团队约定门槛的问题 |

如果材料不足，先说明缺口，再进入对齐；不要用猜测填充关键事实。

建议在材料理解后输出一张“对齐清单”，先把 Agent 能自决策的内容和真正需要提问的内容分开：

```markdown
### 产品向对齐清单

| 问题 | Agent 理解/决策 | 技术影响 | 处理方式 |
|---|---|---|---|
| 删除员工语义 | 软删除，不等同停用 | 影响状态机、唯一约束、列表过滤 | Agent 默认写入/需要用户确认 |
| 账号注销影响范围 | 注销整个账号或仅当前商户身份 | 影响账号状态机、成员联动和合规口径 | 需要用户确认 |

### 技术向对齐清单

| 设计点 | Agent 技术决策 | 影响 | 处理方式 |
|---|---|---|---|
| 后端接口权限校验实现 | 使用 `@RequirePermission` + AOP/Interceptor + PermissionManager | 统一权限校验，避免业务代码写散 | Agent 默认写入 |
| 短信供应商扩展 | 定义 SmsSender 策略接口，V1.0 阿里云实现，预留多供应商路由 | 后续可切换/兜底短信平台，提高触达率 | Agent 默认写入 |
| 支付后余额入账链路 | 支付回调同事务更新订单和支付单，afterCommit 投递入账事件，MQ 消费幂等入账，定时任务兜底对账 | 保证订单、支付、余额流水最终一致，避免重复入账或漏入账 | Agent 默认写入/需要用户确认 |
```

## 推荐设计树

下面是推荐的推演方向。Agent 应根据实际情况增删分支、调整顺序、合并明显无分歧的节点。

执行时按双轨组织：

- **产品向轨道**优先使用 1-5：技术范围继承、核心流程、状态机、技术闭环、DDL/API 契约。重点是把业务语义转成技术边界，不做泛产品评审。
- **技术向轨道**优先使用 6-9：核心技术设计、存量调研、技术选型与系统集成、风险兜底。重点是技术方案、组件边界、扩展约束和工程落地。
- 如果某个问题同时跨两轨，先确认产品语义是否影响技术边界，再进入技术方案设计；不要把技术方案问题提前变成产品问题。

### 1. 技术范围继承确认

推荐推演：

- 上阶段决策是否全部继承。
- 本次范围是否只是任务拆分中的一部分。
- 任务拆分是否遗漏接口、页面、MQ、定时任务、回调处理。
- 是否需要修正上阶段范围、状态机或模块边界。

提问触发：

- 继承决策与本次材料冲突。
- 任务拆分看起来遗漏闭环能力。
- 范围边界会影响文档章节和后续编码职责。

### 2. 核心流程识别

推荐推演：

- 找出真正驱动业务状态变化的核心流程。
- 判断每个流程是新建、改造存量、复用已有能力，还是外部对接。
- 不按接口机械展开，先按业务闭环展开。

提问触发：

- PRD 功能点和接口清单不一致。
- 一个接口可能承载多个业务状态变化。
- 一个业务闭环缺少入口、回调、补偿或查询能力。

### 3. 状态机与状态流转

推荐推演：

- 识别核心业务对象和状态字段。
- 推导每条状态转换路径的触发场景、入口、前置条件、失败出口。
- 检查 DDL 状态字段和枚举是否能承载这些流转。

提问触发：

- 存在无出口状态、失败状态、回滚状态、删除/禁用/注销等敏感状态。
- 状态变化会影响权限、库存、资金、消息、缓存、审计。
- DDL 枚举和流程语义不一致。

### 4. 技术闭环推演

推荐推演：

- 异步回调是否需要查单、补偿、幂等、防重。
- 状态失败后是否需要取消、退款、逆向、恢复。
- 定时任务、MQ、回调、审计、缓存失效是否缺失。
- 外部调用失败、超时、重复通知、部分成功是否有处理。

提问触发：

- PRD 只描述正向路径。
- 关键状态依赖外部系统。
- 出错后会产生数据不一致、资损、权限绕过、账号异常或用户不可恢复状态。

### 5. DDL 与接口契约对齐

推荐推演：

- 请求/响应参数是否有字段承载。
- 状态机、幂等、审计、缓存、软删除、唯一约束是否有数据支撑。
- 按已确认的业务查询、排序、分页和关联访问逐表检查索引承载；只保留唯一索引、规范强制索引和明确业务必需的索引，补充索引必须说明查询场景、字段和必要性。
- DDL 初稿是否需要调整。

提问触发：

- 字段缺失、枚举不完整、唯一索引不足、软删除与重建冲突，或已确认的业务查询缺少必要索引。
- 接口参数和表字段语义不同。
- 技术闭环新增能力需要补表或补字段。

### 6. 核心技术设计与扩展约束

这是技术分析对齐中的高优先级分支。Agent 不应只围绕产品规则、接口清单和 DDL 字段对齐；必须主动识别后续编码容易写散、写死、难扩展的技术方案点，并给出推荐实现形态。

推荐推演：

| 类型 | 常见内容 | 常见实现形态 |
|---|---|---|
| 横切能力 | 鉴权、权限、审计、日志、风控、限流、数据权限、脱敏 | 拦截器、过滤器、自定义注解、AOP、统一上下文、Manager |
| 高敏能力 | 支付、余额、密码、手机号、账号注销、权限变更、状态流转 | Manager、状态机、事务模板、审计日志 |
| 强扩展点 | 权限码、外部渠道、短信/通知供应商、通知模板、策略选择、结算规则、价格规则 | 枚举元数据、策略模式、模板方法、注册表、路由器 |
| 基础设施 | 缓存、幂等、分布式锁、事务后置动作、重试、降级、告警 | CacheManager、IdempotencyManager、LockTemplate、事件机制、afterCommit 回调 |
| 流程推进 | 下单、支付、回调、入账、结算、注销、审批等多阶段链路 | 同步接口、MQ、定时任务、Outbox、本地消息表、状态机/流程编排 |
| 一致性闭环 | 跨表、跨模块、跨服务或外部回调导致的部分成功、重复、乱序、漏处理 | 本地事务、幂等键、唯一约束、状态机、补偿任务、对账任务、人工处理 |

每个设计点至少推演：

- 为什么需要单独设计。
- 推荐实现形态。
- 禁止的原始实现方式。
- 放在哪个模块/包，谁调用谁。
- 后续新增策略、枚举、注解、模板时怎么扩展。
- 失败时如何降级、重试、告警或转人工。
- 为什么选择同步接口/MQ/定时任务/afterCommit/Outbox/状态机等路径，而不是其他路径。
- 数据一致性如何闭环：事务边界、锁、幂等、补偿、对账、人工处理分别落在哪里。

Agent 应主动默认写入的典型技术方案：

| 场景 | 推荐默认方案 | 写入重点 |
|---|---|---|
| 后端接口权限校验 | 自定义权限注解 + AOP/Interceptor + `PermissionManager` | 注解粒度、权限码来源、缓存失效、禁止业务代码散写 |
| 数据范围过滤 | `DataScopeManager` 统一计算数据范围 | 可见对象集合、查询条件构造、越权错误码、禁止前端传范围绕过 |
| 短信发送 | `SmsSender` 策略接口 + 供应商实现 + 路由/兜底策略 | V1.0 主供应商、未来备用供应商、频控、失败告警、触达率兜底 |
| 操作审计 | `OperationAuditManager` + 审计表/日志 | 操作前后摘要、traceId、失败原因、审计失败兜底 |
| 事务后副作用 | afterCommit 执行短信、缓存删除、审计、告警 | 主事务边界、副作用失败是否回滚、补偿方式 |
| 权限码扩展 | 结构化枚举元数据或字典表 | 前端权限树、服务端注解、未来端扩展、发版成本 |
| 外部渠道适配 | Client/Adapter/Strategy 分层 | SDK 隔离、重试、降级、错误码映射 |
| 异步事件推进 | 主事务提交后投递 MQ，消费端幂等处理 | 事件生产时机、消费幂等键、失败重试、死信/告警 |
| 定时补偿对账 | 定时任务扫描处理中/超时/失败状态 | 扫描条件、补偿动作、重试上限、人工介入 |
| 可靠事件 | Outbox/本地消息表承载关键事件 | 主数据与事件同事务落库、后台发送、发送状态补偿 |
| 资金/库存一致性 | 状态机 + 唯一流水 + 幂等消费 + 对账 | 防超卖、防重复支付、防重复入账、防漏记流水 |

只有当默认方案会引入新表、新中间件、新云服务、成本、合规风险或长期架构路线取舍时，才显式询问用户。否则直接作为 Agent 决策写入技术分析。

核心流程技术闭环示例：

```plain
下单
-> 校验商品/价格/库存
-> 锁库存或扣减库存
-> 创建订单和支付单
-> 支付回调幂等处理
-> 更新订单已支付
-> 确认库存消耗
-> afterCommit 投递商家入账事件
-> MQ 消费幂等入账
-> 写入余额流水和审计日志
-> 缓存失效/通知
-> 定时任务兜底查单、补偿和对账
```

这类链路必须同时说明：

- 哪些步骤在同一事务内。
- 哪些步骤异步化，为什么异步。
- 哪些步骤由外部回调推进。
- 哪些步骤由定时任务兜底。
- 哪些步骤需要锁、幂等键、唯一约束或状态校验。
- 哪些步骤需要流水、审计、告警或人工处理入口。

提问触发：

- 写散后会影响多个模块。
- 涉及资金、账号、权限、密码、手机号、状态机等高敏行为。
- 后续扩展概率高，原始实现会导致返工。
- 技术实现有多个可选方案，且会影响 DDL/API、长期架构、成本、合规安全或团队约定，需要用户或团队取舍。

### 7. 存量业务调研

推荐推演：

- 本次是否改造、扩展、复用或对接已有接口。
- 存量接口当前读写哪些表，状态机和事务边界是什么。
- 本次改造是否影响已有调用方和已有数据。

提问触发：

- 材料出现“复用”“改造”“兼容”“对接已有”。
- 新流程会写已有表或依赖已有状态。
- 无代码调研无法判断集成风险。

触发后加载 `legacy-research.md`。调研报告完成前，不基于猜测设计存量集成方案。

### 8. 技术选型与已有系统集成

推荐推演：

- 是否能使用已有技术栈和组件。
- 是否需要新增缓存、锁、MQ、定时任务、短信、文件、外部渠道适配。
- 项目间调用关系、数据同步、状态同步和兜底是否闭环。

提问触发：

- 需要新增依赖或基础设施。
- 存在多个实现路径且影响复杂度、可维护性或上线风险。
- 已有系统的能力边界不明确。

### 9. 风险与兜底

推荐推演：

- 可应对风险和不可规避风险分别是什么。
- 如果核心技术设计漏用或失效，会产生什么后果。
- 是否需要降级、告警、补偿、人工处理入口。

提问触发：

- 风险接受需要业务或技术负责人确认。
- 兜底方案会影响接口、表、任务、监控或运维流程。

## 提问格式

进入逐个提问前，先输出“Agent 默认决策清单”和“需要用户确认清单”。只有“需要用户确认清单”里的问题才进入每轮提问。

沟通表达必须便于扫读：使用轻量 Markdown，在自然描述问题、推演、建议方案和备选方案时，主动将用户最需要关注的**关键词、风险点、取舍点、结论性判断**加粗。不要新增“关键概念”栏目，不要整段加粗；每段只突出少量真正影响判断的内容。

```markdown
我先把能自行决断的方案收敛如下，不逐项打扰你：

| 设计点 | Agent 决策 | 影响 |
|---|---|---|
| {{设计点}} | {{推荐方案}} | {{影响范围/后续扩展/风险}} |

真正需要你参与定义的只有：

| 问题 | 为什么必须你确认 |
|---|---|
| {{问题}} | {{命中业务语义/DDL/API/架构/合规/成本等门槛}} |
```

每轮问题使用这个结构：

```markdown
当前分支：{{设计树分支}}

我的推演：{{基于材料/代码得到的判断；将关键判断点、影响范围、风险点适度加粗}}

既有决策检查：{{若相关，说明是否已有确认结论；已有结论则不要提问，直接继承。只有重议时说明重议原因。}}

发现的问题：{{冲突点/模糊点/闭环缺口/扩展风险；将真正影响决策的内容适度加粗}}

我的建议方案：{{推荐答案；将推荐取舍的核心结论适度加粗}}

建议理由：{{为什么这样定}}

备选方案：{{至少 1 个可行备选；如果不建议采用，说明原因；将备选的主要代价或适用条件适度加粗}}

方案影响：
| 方案 | 优点 | 代价/风险 | 适用条件 |
|---|---|---|---|
| 建议方案 | {{优点}} | {{代价/风险}} | {{适用条件}} |
| 备选方案 | {{优点}} | {{代价/风险}} | {{适用条件}} |

需要你确认：{{一个明确问题}}
```

要求：

- 一次只问一个明确问题。
- 问题必须能影响技术分析结论。
- 问题必须命中用户参与门槛；否则放入 Agent 默认决策清单。
- 推荐答案不能只是“都可以”，必须表达 Agent 的取舍。
- 备选方案必须是真实可落地方案，不能为了凑格式虚构低质量选项。
- 如果只有一个合理方案，也要说明“未推荐备选”的原因，例如备选会破坏一致性、引入不必要成本、违背既有架构或无法满足合规要求。
- 加粗只用于帮助用户快速抓重点：优先标注影响范围、不可逆后果、成本/合规/安全风险、推荐结论和需要用户拍板的核心取舍；不要把普通背景描述或整段文字全部加粗。
- 用户反馈后，先复述最终决策，再进入下一个依赖分支。
- 用户暂时无法确定时，标注“待定”，继续推进不依赖该结论的分支。
- 所有最终决策都记录为：分支、决策点、AI 推荐、用户确认、依据、影响。

## 何时停止盘问

满足以下条件后，先进入“遗漏决策反省”，不能直接进入最终补充确认或步骤 5：

- 产品向轨道已收敛：本次范围已确认；核心流程和状态机已无方向性分歧；关键业务语义、风险接受、DDL/API 冲突已有结论或待定标记。
- 技术向轨道已收敛：技术闭环缺口已补齐或记录为风险；核心技术设计点已明确实现形态、组件边界、扩展方式和失败兜底。
- Agent 默认决策清单已展示：用户知道哪些内容由 Agent 自行决断并会写入正文。
- 必须用户参与的问题已逐个确认或标记待定。
- 存量调研已完成，或明确本次不涉及存量。

## 遗漏决策反省

双轨盘问收敛之后、最终补充确认之前，必须执行一轮“遗漏决策反省”。

前提假设：

> 需求内容细节太多，Agent 或用户都可能遗漏关键决策；即使已经完成 grilling，也要主动假设仍有隐藏分支没有被问到。

### 反省视角清单

遗漏决策反省不是把普通检查项再问一遍，而是换成“挑刺视角”寻找会让编码返工、数据失真、权限失控或上线后难以兜底的隐藏决策。Agent 至少从下面角度中选择与本次范围最相关的 6 个方向扫描；复杂需求可扫全量，但最终只补问少量真正关键的问题。

| 视角 | 追问方式 | 典型遗漏决策 |
|---|---|---|
| 事故后果倒推 | 如果这个方案上线后出事故，最可能是哪类事故？谁会受损？是否不可逆？ | 资损、权限泄露、账号失控、数据污染、用户无法自恢复、客服无法处理。 |
| 反例路径 | 正向流程都通了，失败、撤销、重试、重复提交、部分成功时怎么收场？ | 失败状态、补偿入口、重试策略、重复请求语义、人工处理边界。 |
| 生命周期闭环 | 关键对象是否覆盖创建、启用、编辑、禁用、删除、恢复、归档、注销后的全链路？ | 删除后能否重建、禁用和删除差异、归档后查询口径、历史数据保留。 |
| 身份与权限矩阵 | 谁操作谁？操作者和目标对象是否可能同人、跨商户、跨门店、跨角色层级？ | 自我禁用、删除最后管理员、越权改角色、数据范围越界、角色被删后的表现。 |
| 高敏动作升级 | 这个动作是否改变账号、密码、手机号、权限、资金、实名或关键配置？ | 二次校验、短信/密码验证、token 失效、审计日志、脱敏展示。 |
| 并发与时序 | 两个用户或两个请求同时操作时，不变量是否还能成立？ | 行锁、唯一约束、幂等键、乐观锁、缓存失效顺序、事务边界。 |
| DDL/API 承载力 | 决策是否真的能被字段、索引、枚举、接口参数和响应表达出来？ | 缺字段、唯一索引与软删除冲突、枚举不够、接口缺 requestId 或状态字段。 |
| 跨模块联动 | 本模块状态变化后，哪些模块会读取、缓存、展示或依赖它？ | 权限菜单刷新、员工/门店/角色联动、M9 数据口径、消息通知、登录态刷新。 |
| 可观测与追责 | 出问题时能否定位是谁、何时、对什么对象、从什么值改到什么值？ | 操作日志、审计字段、traceId、失败原因、告警和客服排查入口。 |
| 用户可恢复性 | 用户操作失败或误操作后，是否有自助恢复、再次触发或明确提示？ | 重发短信、重新邀请、撤销/恢复、错误文案、客服处理指引。 |
| V1/V2 边界 | 哪些能力现在不做但将来高概率扩展？当前设计是否堵死未来？ | 预留字段/枚举/接口边界、外部 SDK 替换、渠道扩展、PC/APP 共用权限码。 |
| 材料冲突放大 | PRD、任务拆分、API、DDL、历史决策若各说一半，最危险的解释是哪一种？ | 文案与字段长度不一致、删除语义冲突、手机号账号归属冲突、范围被误扩大。 |
| 沉默角色 | 有没有材料没点名但实际上会受影响的人或系统？ | 客服、运营、审计、测试、运维、下游报表、未来 PC 端、外部供应商。 |
| 不变量守护 | 系统必须始终成立的业务事实是什么？哪些操作会破坏它？ | 一个商户同手机号只能有一个有效员工、权限不能超出操作者、至少一个管理员。 |

筛选规则：

- 优先补问会改变 DDL、接口契约、权限模型、状态机、事务/锁/幂等或模块边界的问题。
- 能从材料、代码、DDL 或既有决策直接推出的，写入“已确认继承”或“默认写入”，不要问用户。
- 产品/技术交叉问题如果 Agent 能基于材料和工程常识给出稳妥决策，先写入“Agent 默认决策”并说明影响，不进入补问。
- 只属于实现细节且不影响对外契约的，默认写入技术分析，不进入补问。
- 纯技术方案级内容应优先由 Agent 决断并写入，例如权限注解、策略模式、多供应商适配、缓存失效、事务后置动作；只有引入新表/新中间件/成本/合规风险/长期架构路线时才补问。
- 只属于远期能力但当前不能定稿的，记录为风险/待定，不拖住大纲确认。

执行方法：

1. 重新回扫本次范围和已确认决策索引，不重复打开已确认问题。
2. 按“反省视角清单”挑选最相关的视角扫描，不满足于范围边界、业务规则、状态机、DDL/API、事务/锁/幂等、权限安全、数据范围、脱敏审计、原生能力、外部依赖、风险兜底等表层分类。
3. 输出候选遗漏点表格，按处理方式分类：
   - `已确认继承`：已有明确决策，正文引用来源，不再提问。
   - `Agent 默认决策`：Agent 可自行决定的产品/技术交叉或纯技术方案，列出决策和影响，不提问。
   - `需要补问`：会影响接口、DDL、状态机、事务、安全或编码边界，必须逐个问。
   - `默认写入`：可按材料和工程常识直接写入，不需要用户拍板。
   - `记录风险/待定`：当前无法定稿，但不阻塞正文。
4. 只选择少量真正关键的 `需要补问` 项继续逐个提问；不得把候选表格中的所有问题机械问完。
5. 遗漏决策反省最多执行两轮。若第一轮后仍明显担心遗漏，可执行第二轮；第二轮结束后必须收敛为已补问、继承、Agent 默认决策、默认写入、风险或待定，不得继续扩散。
6. 收敛后执行最终补充确认。用户确认无补充后，才进入目录大纲确认。

建议输出格式：

```markdown
我假设自己和你都可能漏掉关键决策，重新回扫后发现这些候选：

| 反省视角 | 候选遗漏点 | 影响 | 处理方式 |
|---|---|---|---|
| {{事故后果/反例路径/权限矩阵等}} | {{问题}} | {{影响}} | {{已确认继承/Agent 默认决策/需要补问/默认写入/记录风险}} |

我建议只补问其中 {{N}} 个真正影响编码边界的问题，其余按继承/默认/风险处理。
```

## 最终补充确认

沟通对齐的最后一个环节必须执行最终补充确认。Agent 先汇总当前已对齐内容，再问用户是否还有任何需要补充、澄清或调整的内容。

必须给出可能补充方向，帮助用户回忆遗漏点：

- 范围边界：是否还有本次要覆盖/不覆盖的模块、接口、页面、任务、MQ、回调。
- 业务规则：是否还有 PRD 未写清的校验、状态、异常、失败处理、人工处理规则。
- 技术闭环：是否还缺查单、补偿、重试、幂等、锁、缓存失效、审计、告警、降级。
- 数据模型：是否还有字段、枚举、唯一约束、软删除、历史记录、审计日志需要补充。
- 权限与安全：是否还有权限码、接口鉴权、数据权限、脱敏、账号/密码/手机号等高敏约束。
- 存量兼容：是否还有已有接口、已有数据、已有调用方、迁移或兼容要求。
- 扩展设计：是否还有未来高概率扩展的策略、渠道、模板、状态流转、配置化能力。
- 风险兜底：是否还有可接受风险、不可接受风险、上线兜底或运维处理要求。

建议提问格式：

```markdown
目前我理解我们已经对齐了：
- 产品向：{{范围、核心流程、状态机、业务语义、风险接受}}
- 技术向：{{核心技术设计、组件边界、DDL/API、事务/锁/幂等、缓存/审计/兜底}}
- Agent 默认决策：{{自行决断并写入正文的设计点}}
- 需要用户确认的决策：{{已确认/待定项}}

在进入大纲前，请再确认是否还有需要补充或澄清的内容？
可以按两条线检查：
- 产品向：范围边界、业务规则、状态语义、异常处理、风险接受。
- 技术向：架构组件、扩展设计、DDL/API、权限安全、数据范围、幂等锁事务、缓存审计、存量兼容、风险兜底。

我的建议：如果没有新增内容，我们就进入目录大纲确认；如果有，请先补充，我会把它纳入技术分析决策。
```

只有用户明确回复“没有补充”“无”“可以进入大纲”“确认进入下一步”等含义后，才可以进入步骤 5 大纲确认。若用户补充了新内容，回到对应设计树分支继续 grilling，直到再次完成最终补充确认。

步骤 5 大纲必须体现：范围、继承决策、核心技术设计与扩展约束、数据模型、状态机、核心流程、风险与兜底，以及按需章节。
