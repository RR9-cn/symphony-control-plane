# fskill-analysis-tech - 技术分析文档撰写

## 流程规约

使用本 skill 时，**不允许跳过说明步骤直接输出技术分析正文**。第一轮必须先说明：已进入本 skill、已/待定位哪些输入材料、待圈定的技术分析范围、后续必须经过的确认卡点。

固定流程闸门：

1. 步骤 0/1：获取迭代上下文，自动定位或补充收集输入材料。
2. 步骤 2：圈定本次技术分析范围。
3. 步骤 3：通读材料，按“产品向/技术向”双轨总结关键信息、继承决策、技术栈约束、疑似核心技术设计点、Agent 默认决策和必须用户拍板项。
4. 步骤 4：按双轨决策树沟通对齐。产品向只确认会影响技术边界的范围、业务语义、状态规则和风险接受；技术向重点确认架构边界、组件模式、扩展约束、技术方案选型、核心流程技术闭环、数据一致性闭环、事务幂等、权限安全、DDL/API 承载和风险兜底。进入盘问前必须先复读并汇总既有 `decision-log.md` / DDL 假设 / 上轮技术分析中的已确认决策；已确认的同一问题只能作为继承结论引用，禁止再次向用户确认，除非本次材料出现新的冲突或用户主动要求重议。
5. 步骤 4.5：遗漏决策反省。完成步骤 4 的双轨对齐后、最终补充确认前，必须显式执行一轮“遗漏决策反省”：假设需求细节太多，Agent 或用户可能遗漏关键决策，按 `references/alignment-decision-tree.md` 的反省视角清单，从事故后果、反例路径、身份权限、生命周期、并发幂等、跨模块联动、DDL/API 承载力、可恢复性和风险兜底等方向主动挑刺，列出候选遗漏点并筛选真正需要补问的少量问题。该反省流程最多执行两轮；第二轮结束后必须收敛为“已补问/继承/Agent 默认决策/默认写入/记录为风险或待定”，不得无限延长盘问。收敛后再做最终补充确认，用户确认无补充后才进入步骤 5。
6. 步骤 5：输出目录大纲并等待用户明确确认。
7. 步骤 6：按确认后的大纲撰写技术分析正文。
8. 步骤 7：执行多视角 review，并处理确认结果。
9. 步骤 8：保存产物、追加决策记录并交付摘要。

若用户回复“继续”“确认”“可以”，先判断当前处于哪个闸门，只推进到下一步；不得跨过尚未完成的范围确认、大纲确认或 review 确认直接交付最终文档。

若执行 Agent 是 **Codex**，进入本 skill 后立刻创建任务/计划（如 `update_plan` 或等价 Todo 工具），至少包含：定位输入、圈定范围、双轨通读总结、双轨沟通对齐、遗漏决策反省、大纲确认、撰写、Review、交付。每完成一个闸门就更新任务状态。任务计划只作为流程护栏，不能替代用户明确确认。

若用户要求“直接输出技术分析”，仍需完成最小流程：明确范围、继承决策、确认大纲；缺少确认时只能输出待确认项和下一步，不能输出最终技术分析正文。

## 定位

本 skill 负责基于已有材料撰写技术分析文档，目标是让开发团队可以据此进入编码阶段。

输入来自产品文档、接口文档、DDL 变更设计、任务拆分表格、上阶段决策记录、技术栈设计信息和必要的存量代码调研。

输出聚焦系统架构、核心技术设计与扩展约束、数据模型、核心流程、风险与兜底，不做 PRD 评审、任务拆分、DDL 专项设计或业务代码实现。

## 执行流程

### 步骤 0 - 获取迭代上下文与自动定位输入

执行 `fshows --json workflow status`，提取 `data.current.featureRoot`、`data.current.iteration`、`data.current.feature`。命令失败不阻塞，改为向用户补充询问缺失路径。

在 `featureRoot` 下自动定位输入材料，读取已找到文件，并向用户简要汇报“已定位/未定位”清单。

### 步骤 1 - 补充收集输入

只询问步骤 0 未定位到的必须输入。若找不到上阶段决策记录或技术栈设计信息，也说明缺失并询问是否跳过。

收集完后告知默认产物保存位置。

### 步骤 2 - 圈定本次技术分析范围

解析任务拆分表，列出模块、接口、页面、MQ 消费者、定时任务、回调处理等清单，让用户选择本次覆盖范围。

后续所有步骤只针对已圈定范围展开，技术分析文档概览必须标明范围。

### 步骤 3 - 通读材料并总结关键信息

只通读与本次范围相关的材料，提取业务背景、接口清单、数据模型、核心流程、状态机、技术栈约束、继承的上阶段决策和疑似核心技术设计点。

必须结合已确认的业务查询场景，逐表评估现有索引和 DDL 初稿是否足以支撑查询、排序、分页和关联访问；遵循最小索引原则，除唯一索引、规范强制索引和已明确为业务必需的索引外一律不新增。需要补充索引时，必须明确记录查询场景、涉及字段、索引定义和必要性；无法明确业务用途的索引不加。

涉及已有表时，若项目配置了 `.fshows/db-config.yaml`，使用 `fshows` 查询真实表结构；需要 SQL 工具细节时加载 `fskill-tools-db`。

向用户展示材料理解时必须按双轨输出：

- 产品向：本次范围、继承的上阶段决策、核心路径、业务语义/状态/风险冲突点、产品向 Agent 默认决策、产品向必须用户拍板项。
- 技术向：技术栈约束、技术闭环候选、疑似核心技术设计点、技术方案选型候选、数据一致性闭环候选、核心流程技术闭环候选、可自行查证项、技术向 Agent 默认决策、技术向必须用户拍板项。

等待用户确认或修正后，再进入逐点沟通对齐。

### 步骤 4 - 沟通对齐

加载 `references/alignment-decision-tree.md`，以 grilling 式盘问完成双轨对齐：先基于材料和代码自行推演，再沿设计树逐分支深挖真实的技术闭环、冲突点和模糊点。决策树是推荐方向，不是机械问卷；每轮只问一个决策点，并给出建议方案、备选方案、取舍理由和影响。对齐沟通要便于扫读，在自然描述中适度加粗用户最该关注的判断点、风险点、取舍点和结论，不新增额外栏目，不整段加粗。

对齐时必须先输出“Agent 默认决策清单”和“需要用户确认清单”。能由 Agent 基于材料、代码、DDL、既有架构和工程常识稳妥决断的问题，写入 Agent 默认决策，不直接提问；只有命中业务语义、DDL/API 契约、长期架构、合规安全、外部依赖或成本等用户参与门槛的问题才逐个提问。

技术向对齐必须对每个核心流程输出推荐实现路径：同步接口、MQ、定时任务、afterCommit、Outbox/本地消息表、状态机/流程编排如何组合；同时说明为什么不用其他路径，以及事务、锁、幂等、补偿、对账、告警、人工处理如何构成数据一致性闭环。

开始盘问前，必须建立“已确认决策索引”：读取并提取 `decision-log.md` 中任务拆分阶段、DDL 阶段、技术分析阶段的确认项，以及 DDL `设计假设与待确认项` 中状态为“已确认”的条目。若已有决策覆盖当前问题，直接继承并在本次技术分析中标注来源，不得重复提问。只有当本次范围发现新的冲突、实现约束变化或用户明确要求重新决策时，才允许把已确认结论重新提出给用户。

沟通对齐结束前，必须汇总产品向结论、技术向结论、Agent 默认决策和必须用户确认项。步骤 4 不做最终补充确认；最终补充确认统一放在步骤 4.5 遗漏决策反省收敛之后执行。

对齐结论先记录在工作上下文中，步骤 8 再统一追加到 `decision-log.md`。

### 步骤 4.5 - 遗漏决策反省

在步骤 4 结束、最终补充确认前，必须执行“遗漏决策反省”。该流程的前提假设是：需求内容细节太多，Agent 或用户都可能遗漏影响编码边界的关键决策。

执行方式：

1. 回扫本次范围、已确认决策索引、PRD/接口/DDL/任务拆分冲突点、核心流程、状态机、权限安全、原生能力、风险兜底，并使用 `references/alignment-decision-tree.md` 中的反省视角清单做一次“挑刺式”扫描。
2. 列出“可能遗漏的关键决策候选”，并标注处理方式：已确认可继承、需要补问、可按默认方案写入、记录为风险/待定。
3. 只对真正影响技术分析结论和编码边界的点继续逐个补问；不要把所有候选都抛给用户。
4. 该流程最多执行两轮。若第一轮补问后用户要求再反省一次，可以执行第二轮；第二轮后必须收敛，不得继续扩散问题。
5. 收敛后做最终补充确认；用户确认无补充后，才进入步骤 5。

### 步骤 5 - 对齐目录大纲

根据已确认范围、材料理解、双轨对齐决策、遗漏决策反省结论和 `references/writing-standards.md` 提出目录大纲。

大纲必须能承接：产品向业务约束、技术向核心设计、技术方案选型、核心流程技术闭环、数据一致性闭环、Agent 默认决策、用户确认决策、待定/风险项；不得只按接口清单机械展开。

必须收到用户明确确认后，才进入步骤 6；确认后可细化二级/三级标题。

### 步骤 6 - 迭代撰写

加载 `templates/tech-analysis.md` 和 `references/writing-standards.md` 开始撰写。写核心流程步骤卡片时加载 `references/operation-matrix.md`；涉及 DDL/字段/索引时加载 `references/ddl-conventions.md`。

按确认后的大纲逐章写作。撰写中新发现的技术决策点必须记录，不能只写结论。

### 步骤 7 - 多视角 Review

正文完成并自查无明显矛盾后，加载 `references/review-checklist.md`，分别从架构师视角和资深开发视角 review。

将高/中/低风险项展示给用户逐项确认。高/中级问题未处理或未记录为已知风险前，不进入交付。

### 步骤 8 - 交付

保存技术分析文档，追加 `decision-log.md`，按需保存存量业务调研报告。

向用户交付：文件路径、改动清单、技术分析摘要、决策记录摘要、review 结果摘要。

## 资源加载路由

只在对应阶段加载相关资源，避免一次性把所有细节读入上下文。

| 阶段 | 何时加载 | 读取资源 |
|---|---|---|
| DDL 对齐 | 涉及表结构、字段、状态枚举、索引、软删除 | `references/ddl-conventions.md` |
| 沟通对齐 | 步骤 3/4/4.5/5，需要双轨 grilling 式盘问核心流程、状态机、技术方案选型、数据一致性闭环、冲突点、模糊点、扩展约束和遗漏决策 | `references/alignment-decision-tree.md` |
| 存量调研 | 涉及已有接口改造/扩展/对接 | `references/legacy-research.md` |
| 撰写正文 | 步骤 6 开始写技术分析文档 | `templates/tech-analysis.md`、`references/writing-standards.md` |
| 写核心流程 | 编写 PlantUML、Step Card、分支步骤、资金标记 | `references/operation-matrix.md` |
| 多视角 Review | 步骤 7 review | `references/review-checklist.md` |

读取资源后，遵循资源内的固定格式；若资源与用户确认的决策冲突，以用户确认的决策为准，并写入 `decision-log.md`。

## Guardrails

- 禁止跳过流程规约直接写正文；范围确认、大纲确认、review 确认是硬卡点。
- 技术分析只针对步骤 2 圈定范围，不对整个 PRD 做全量技术分析。
- 不能进入编码，不创建或修改业务代码、配置、DDL 脚本。
- 不能编造已有表、已有接口、已有技术栈；涉及真实系统时必须基于材料、数据库查询或代码调研。
- 涉及存量业务改造/扩展/对接时，必须按 `references/legacy-research.md` 调研后再设计。
- 决策记录必须追加写入 `decision-log.md`，不覆盖上阶段内容。
- 上游 DDL/API/任务拆分是初步分析，可提出调整；调整原因、前后差异和最终决策必须写入技术分析文档和决策记录。
- 最终交付前必须通过多视角 review；未处理的高/中级问题必须经用户确认并记录为风险。

## 持续改进

- 只有具备跨迭代复用价值的流程、格式、质量规则才写入本 skill；项目个案决策写入对应迭代文档。
- 修改输出结构或固定格式时，同步检查 `templates/tech-analysis.md` 和 `references/` 是否需要更新。
- 每次更新后做最小校验：frontmatter、章节引用、资源路由、模板引用、重复规则。
